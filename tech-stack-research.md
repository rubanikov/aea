# Tech Stack Research — Patient Appointment & Scheduling Portal

Research date: 2026-08-10. Every non-obvious claim below is sourced to the vendor's own docs/pricing/repo at the linked URL, fetched on this date — free tiers and rate limits change, so treat any figure here as "current as of 2026-08-10," not as a permanent fact. Time/timebox is explicitly excluded from the evaluation criteria per the requester; options are judged only on: (1) concurrency/correctness fit, (2) PHI/HIPAA-RBAC fit, (3) free-tier sufficiency (limits, overage behavior, credit-card requirement), (4) ecosystem/testing maturity, (5) deployment/operational simplicity.

## 0. Shared foundation: what Postgres itself guarantees

Both database candidates (Supabase, Neon) are unmodified PostgreSQL, so the core concurrency primitives are identical on both:

- `SELECT ... FOR UPDATE` acquires an exclusive row lock that blocks other transactions from locking or modifying the same rows until the holder commits/rolls back; `NOWAIT` fails immediately instead of blocking, `SKIP LOCKED` silently skips already-locked rows (useful for queue-style dispatch, e.g. the reminder job) — [PostgreSQL docs, SELECT §Locking Clause](https://www.postgresql.org/docs/current/sql-select.html).
- A `UNIQUE` constraint is enforced by an automatically-created B-tree index, not just an application-level check — the index itself is what makes a concurrent duplicate insert impossible to commit; by default two `NULL`s are *not* considered equal (so `NULLS NOT DISTINCT` is needed if a nullable column must also be unique) — [PostgreSQL docs, DDL §Unique Constraints](https://www.postgresql.org/docs/current/ddl-constraints.html).
- This means the brief's two required guards — row-lock the slot before booking, and a unique constraint on `(provider_id, slot_start)` or equivalent as a belt-and-suspenders backstop — are both native, first-class Postgres features on either vendor, not something either platform layers on top.

The one platform-specific wrinkle is **connection pooling**. Both Supabase and Neon default their pooled connection string to **PgBouncer-family transaction-mode pooling**:

- Supabase's pooler (Supavisor, or a co-located PgBouncer on paid plans) offers session mode (port 5432) and transaction mode (port 6543); transaction mode "does not support prepared statements" and session-level features are restricted to session mode or a direct connection — [Supabase docs, Connecting to Postgres](https://supabase.com/docs/guides/database/connecting-to-postgres), [Supabase docs, Supavisor terminology](https://supabase.com/docs/guides/troubleshooting/supavisor-and-connection-terminology-explained-9pr_ZO).
- Neon's pooler is PgBouncer itself in `pool_mode=transaction`; not supported on pooled connections: `SET`/`RESET`, `LISTEN`/`NOTIFY`, `WITH HOLD` cursors, SQL-level `PREPARE`/`DEALLOCATE`, and **session-level advisory locks** — [Neon docs, Connection pooling](https://neon.com/docs/connect/connection-pooling).
- PgBouncer's own docs confirm the mechanism both platforms build on: in transaction mode "a server connection is assigned to a client only during a transaction... the server will be put back into the pool" once the transaction ends — [pgbouncer.org, Features](https://www.pgbouncer.org/features.html).

**Practical takeaway:** a single ORM transaction block (`BEGIN` → `SELECT ... FOR UPDATE` → `UPDATE`/`INSERT` → `COMMIT`) stays on one server connection for its whole duration under transaction-mode pooling on *either* platform, so the booking engine's row-lock pattern is safe on both. What breaks on both is anything relying on **session state outliving a single transaction** — session-scoped `pg_advisory_lock` (as opposed to the transaction-scoped `pg_advisory_xact_lock`), `LISTEN/NOTIFY`, and driver-level prepared-statement caching (must be disabled per Supabase's own guidance). None of these are needed for the booking guard itself, so this is a non-issue as long as the ORM's standard transaction block is used rather than a hand-rolled multi-request lock.

## 1. Backend framework — Ruby on Rails vs Node/Express vs Django

| Option | Pros | Cons | Concurrency-primitive maturity |
|---|---|---|---|
| **Ruby on Rails** (ActiveRecord) | `.lock` / `.lock!` generates `SELECT ... FOR UPDATE` directly; `record.with_lock { }` wraps the lock + transaction in one call — [Rails Guides, Active Record Querying §Locking](https://guides.rubyonrails.org/active_record_querying.html). Built-in optimistic locking via a `lock_version` column raises `ActiveRecord::StaleObjectError` on stale writes, a second correctness layer for free. | Custom lock modes (e.g. `NOWAIT`/`SKIP LOCKED`) require passing a raw SQL string into `.lock("...")` — the guide's only documented example is `lock("LOCK IN SHARE MODE")`, i.e. there's no first-class `nowait:`/`skip_locked:` keyword arg the way Django has. | High — native FOR UPDATE support, but NOWAIT/SKIP LOCKED are string-typed, not a documented API surface. |
| **Django** (ORM) | `select_for_update(nowait=False, skip_locked=False, of=(), no_key=False)` is a first-class, explicitly-typed method — `nowait`/`skip_locked` are real keyword args (mutually exclusive; passing both raises `ValueError`) — [Django docs, QuerySet API §select_for_update](https://docs.djangoproject.com/en/stable/ref/models/querysets/). Must run inside `transaction.atomic()`; calling it under autocommit raises `TransactionManagementError`, which fails loudly rather than silently no-op'ing. | **SQLite silently ignores `select_for_update()`** — "no error is raised" and no `FOR UPDATE` clause is added — a real trap if a dev defaults to SQLite locally and only discovers the guard does nothing once running against real Postgres. `TestCase` wraps each test in one transaction, so testing true cross-connection locking requires the heavier `TransactionTestCase` (same doc). | High — same DB-level guarantee, more explicit API, but a silent-no-op footgun on SQLite. |
| **Node/Express** (+ Prisma or Drizzle) | Prisma: transactions are supported via `$transaction(async (tx) => {...})` interactive transactions — [Prisma docs, Transactions](https://www.prisma.io/docs/orm/prisma-client/queries/transactions). Drizzle: a `.for('update')` chainable method exists on Postgres select queries. | **Prisma has no native `FOR UPDATE` API at all** — a GitHub feature request for it (`Row locking support via FOR UPDATE`, issue #17136) is still open with no maintainer commitment — [prisma/prisma#17136](https://github.com/prisma/prisma/issues/17136). The only path is raw SQL (`tx.$queryRaw`/`tx.$executeRaw`) issued inside an interactive transaction — undocumented as a pattern on Prisma's own transactions page. Drizzle's `.for('update')` **exists in the codebase but is undocumented on the official docs site** — an open docs issue confirms "Drizzle has SELECT FOR UPDATE support... but this is not documented anywhere" — [drizzle-team/drizzle-orm#2875](https://github.com/drizzle-team/drizzle-orm/issues/2875). | Lowest of the three — correct locking is achievable but requires raw SQL (Prisma) or an undocumented API (Drizzle); nothing enforces or even documents the correct pattern. |

**Recommendation:** Rails and Django both give the booking engine a native, well-documented `SELECT ... FOR UPDATE` primitive baked into the ORM — this is exactly the "DB-level transactional row lock" the brief mandates, with no raw SQL required. Node + Prisma is the weakest fit for this specific requirement: pessimistic locking isn't in Prisma's API surface at all (confirmed by the still-open GitHub issue), so the concurrency-critical code path would be the one part of the app not exercised through the ORM's normal, tested query layer — a correctness risk in exactly the area the brief weights heaviest (20/100 points, pass/fail gate). Node + Drizzle is viable (the lock exists) but its complete absence from the official docs means a developer has to already know to look for it via GitHub issues rather than the documentation — worse discoverability than either Rails or Django. Between Rails and Django, Django's `select_for_update(nowait=, skip_locked=)` is the more explicit, self-documenting API for this exact feature — but its SQLite silent-no-op means the automated concurrency test the brief requires **must** run against real Postgres, never the SQLite default, or it will falsely pass.

## 2. Database + Auth — Supabase vs Neon

| Option | Pros | Cons | Free-tier specifics |
|---|---|---|---|
| **Supabase** (Postgres + Auth) | Row Level Security (RLS) policies are enforced at the Postgres layer itself — "Policies are Postgres's rule engine," adding an implicit `WHERE` to every query regardless of access path (defense in depth even against a compromised app server) — [Supabase docs, RLS](https://supabase.com/docs/guides/auth/row-level-security). Supabase Auth issues JWTs with `auth.uid()` available inside RLS policies, so a `provider_id = auth.uid()` policy maps directly to the brief's "provider sees only their own schedule" requirement with zero app-layer code — [Supabase docs, Auth overview](https://supabase.com/docs/guides/auth). Encryption at rest (AES-256, non-optional, no config needed) is standard across all projects. | Free projects are **paused after 1 week of inactivity** and require a manual unpause from the dashboard — [Supabase Pricing](https://supabase.com/pricing). HIPAA/BAA is gated behind the paid **Team plan** as an add-on — confirmed directly on Supabase's own pricing page ("HIPAA available as paid add-on" starting at Team) — [Supabase Pricing](https://supabase.com/pricing), [Supabase docs, HIPAA Projects](https://supabase.com/docs/guides/platform/hipaa-projects). | 500 MB database (shared CPU/RAM), 2 active projects, 5 GB egress, 1 GB file storage, 50,000 MAUs, 1-hour log retention, **no backups included** — [Supabase Pricing](https://supabase.com/pricing). Credit card not required per widespread third-party reporting, but Supabase's own docs/FAQ don't state this explicitly either way — [Supabase Billing FAQ](https://supabase.com/docs/guides/platform/billing-faq) (silent on the question). |
| **Neon** (Postgres only) | Compute **auto-suspends after 5 minutes idle and auto-resumes on the next query "within a few hundred milliseconds," with no manual dashboard action** — a materially simpler operational story than Supabase's week-long pause + manual unpause — [Neon docs, Scale to Zero](https://neon.com/docs/introduction/scale-to-zero). Free plan is explicitly "not a trial" / permanent, no credit card required, per Neon's own pricing page — [Neon Pricing](https://neon.com/pricing). | No bundled Auth/RLS-policy product with the same first-class integration as Supabase — Neon does offer an optional "Neon Auth"/Data API, but Neon's own HIPAA docs state these **fall outside the HIPAA/BAA boundary and must not be used for PHI** — [Neon docs, HIPAA Compliance](https://neon.com/docs/security/hipaa). RBAC must therefore be hand-rolled as explicit server-side `WHERE owner_id = current_user` checks in every query/service — more surface area for a developer to forget a check than DB-enforced RLS. HIPAA/BAA requires the paid **Scale plan** — [Neon docs, HIPAA Compliance](https://neon.com/docs/security/hipaa). | 0.5 GB storage/project, 100 CU-hours/project/month compute, 100 projects, 10 branches/project, 5 GB egress, 60,000 MAUs (if using Neon Auth) — [Neon Pricing](https://neon.com/pricing). |

**Recommendation:** Supabase is the better fit specifically for the RBAC requirement — the brief itself names "Postgres RLS" as the preferred mechanism for "row-level ownership" checks, and Supabase's RLS + `auth.uid()` integration implements that pattern with policies the database enforces regardless of what queries the app code happens to run, rather than relying on every service method remembering an ownership filter. Neon is a perfectly fine pure-Postgres choice — its auto-resume behavior is operationally simpler than Supabase's weekly pause — but choosing it means accepting hand-written app-layer RBAC as the sole enforcement layer (still explicitly allowed by the brief: "Postgres RLS **or** explicit server-side checks"). Neither vendor's free tier includes HIPAA/BAA coverage — both require upgrading to a specific paid tier (Team for Supabase, Scale for Neon) before real PHI could legally be stored — this should be stated plainly in the submission's README as the brief requires.

## 3. Backend hosting — Render vs Railway

The requirement this section is really testing is: **can the free tier run a persistent, Postgres-backed reminder-dispatch worker/cron process at $0?**

| Option | Pros | Cons | Free-tier specifics |
|---|---|---|---|
| **Render** | Free web service gets 750 instance-hours/month per workspace — enough for one always-on service — [Render docs, Deploy for Free](https://render.com/docs/free). HIPAA-enabled workspaces (paid) get audit logs, RBAC, and disk/snapshot encryption at rest by default — [Render docs, HIPAA Compliance](https://render.com/docs/hipaa-compliance). | **Free instances flatly do not support Background Worker or Cron Job service types** — "Other service types don't support Free instances," confirmed on Render's own free-tier docs — [Render docs, Deploy for Free](https://render.com/docs/free). Cron Jobs carry a documented **$1/month minimum charge** even at near-zero usage — [Render docs, Cron Jobs](https://render.com/docs/cronjobs). Free web services **spin down after 15 minutes with no inbound traffic** and take about a minute to cold-start — [Render docs, Deploy for Free](https://render.com/docs/free) — which also kills any in-process `setInterval`-style reminder scheduler the moment the dyno sleeps, since there's no traffic to keep it warm. Free Postgres (if used instead of Supabase/Neon) expires 30 days after creation, then gets a 14-day grace period, then is **deleted** — [Render Changelog, 30-day Postgres expiry](https://render.com/changelog/free-postgresql-instances-now-expire-after-30-days-previously-90). HIPAA-enabled workspaces require Scale/Enterprise plus a 20% usage surcharge, and explicitly **"cannot deploy or run free instances"** at all — [Render docs, HIPAA Compliance](https://render.com/docs/hipaa-compliance). | 750 free web-service hours/month; Starter (cheapest paid) instance commonly reported at $7/month (Render's own pricing table did not render for automated fetch; a July-2026-dated figure on Render's own blog cites "an always-on Starter web service plus a Basic-256mb Postgres instance... typically ran about $13/month" as a real-world combined example) — [Render, hosting cost article](https://render.com/articles/how-much-does-cloud-application-hosting-cost-for-small-businesses). |
| **Railway** | New accounts get a **$5 one-time credit for 30 days with no credit card required** ("Trial Plan") — [Railway docs, Free Trial](https://docs.railway.com/reference/pricing/free-trial), [Railway docs, Pricing FAQ](https://docs.railway.com/pricing/faqs). Unlike Render, Railway has **no blanket rule against background/worker service types on the free tier** — a cron-configured service just needs to fit inside the credit budget. Cron jobs run on a schedule as low as every 5 minutes and are billed only for actual execution time, so a lightweight "check for due reminders" job that runs briefly and exits would consume very little of the monthly credit — [Railway docs, Cron Jobs](https://docs.railway.com/reference/cron-jobs). | After the 30-day/$5 trial, the account reverts to a "Free" plan with only **$1/month of credit**, capped at 1 GB RAM / shared vCPU / 5 services per project — [Railway docs, Free Trial](https://docs.railway.com/reference/pricing/free-trial). Railway's cron jobs are explicitly **not for long-running processes** — "Services configured as cron jobs are expected to execute a task, and terminate as soon as that task is finished... [not] for long-running processes that don't exit" — [Railway docs, Cron Jobs](https://docs.railway.com/reference/cron-jobs) — so a genuinely 24/7 worker (rather than a periodic dispatch check) would run as a normal always-on service and likely burn through the $1/month credit quickly. HIPAA BAA is an Enterprise add-on gated behind "a paid monthly spend threshold" — [Railway docs, Compliance](https://docs.railway.com/enterprise/compliance). | $5/30-day trial credit, no card; reverts to $1/month credit afterward. |

**Recommendation:** Railway is the better fit for the reminder-dispatch requirement specifically because Render's free tier has a hard, documented wall against any background worker or cron service — "Other service types don't support Free instances" is unambiguous, and Render's own cron product costs a minimum of $1/month, which technically violates the brief's "100% free tier, no paid API required" constraint if run natively on Render. Railway's cron-job model (short-lived, scheduled, billed per second) is a much more natural fit for a periodic "scan for due reminders and dispatch" job living inside a small monthly credit. If Render is preferred for the always-on web API (its 750 free hours are generous), the reminder job would need an external free trigger — e.g. a scheduled GitHub Actions workflow or a third-party free cron-ping service — hitting an authenticated dispatch endpoint, since nothing inside Render itself can run that job for free.

## 5. Email reminders — Resend (default), Twilio (paid SMS note)

| Option | Pros | Cons | Free-tier specifics |
|---|---|---|---|
| **Resend** | Purpose-built transactional email API, straightforward send/receive model. | **No BAA offered** — a search of Resend's own privacy policy for HIPAA/PHI/BAA language returns nothing; Resend does not support HIPAA-regulated email content — [Resend Privacy Policy](https://resend.com/legal/privacy-policy). This means reminder email **bodies must never contain PHI** — matches the brief's own suggested mitigation ("send a generic reminder + secure link" rather than PHI-bearing content) rather than contradicting it, but it's a hard requirement, not a nice-to-have, given Resend's lack of a BAA path at any tier. | 3,000 emails/month, capped at **100/day**, 1 domain, 30-day data retention — [Resend Pricing](https://resend.com/pricing). Next tier (Pro, $20/mo) raises this to 50,000/month with no daily cap (same source). |

**Twilio (paid SMS, not required):** Twilio charges **$0.0083 per SMS segment** for US outbound messages, plus a separate carrier fee (roughly $0.0025–$0.005/message depending on carrier) that Twilio passes through on top of its base rate, and phone numbers start at $1.15/month — [Twilio SMS Pricing (US)](https://www.twilio.com/en-us/sms/pricing/us). Since email already satisfies the brief's reminder requirement and Twilio is explicitly a paid, optional add-on, it isn't evaluated further here — the free-tier constraint alone rules it out as a required component.

**Recommendation:** Resend is the only real option and is sufficient for the brief's scale (a 10-provider, ~16,000-slots/year clinic sending one 24-hour-prior reminder per appointment is nowhere near 100 emails/day at any realistic demo/grading volume). The one load-bearing operational rule this generates: reminder email bodies must stay PHI-free (appointment-generic text + a link into the authenticated app), which the brief already recommends as best practice — Resend's lack of a BAA makes it a hard requirement rather than optional hardening.

Ollama is the most PHI-safe by construction (nothing ever leaves the machine) but is impractical to run inside any of the free hosting tiers above — better suited as a documented local-only alternative in `AI_USAGE.md` than as the model actually running in the deployed demo.

## Recommended stack summary

| Layer | Recommendation |
|---|---|
| Backend framework | **Django** — `select_for_update(nowait=, skip_locked=)` is a first-class, explicitly-typed API mapping directly to the no-double-booking guard (Rails' ActiveRecord `.lock!`/`with_lock` is an equally valid substitution if the team is Ruby-first; avoid Node+Prisma for the concurrency-critical path — no native FOR UPDATE support, confirmed by an unresolved upstream GitHub issue). |
| Database + Auth | **Supabase** — Postgres-level RLS enforced via `auth.uid()` maps directly to the brief's patient/provider/admin row-ownership requirement with less app-layer code to get wrong than Neon's hand-rolled RBAC checks. |
| Backend hosting | **Railway** — free/trial credit can actually run a scheduled reminder-dispatch cron job; Render's free tier explicitly forbids any background worker/cron service type. |
| Frontend hosting | **Vercel** — first-party Next.js integration plus a self-serve Pro-plan BAA path, versus Netlify's enterprise-sales-only HIPAA gate. |
| Email reminders | **Resend** — free tier (3,000/mo, 100/day) comfortably covers the brief's scale; no BAA available, so reminder bodies must stay PHI-free by design. |
| AI/LLM (optional) | **Groq** — free, no card, fastest inference, documented per-model rate limits, and (unlike Resend or Gemini's free tier) an actual BAA program — though it excludes free usage, so synthetic-only inputs remain mandatory regardless of which LLM option is chosen. |
