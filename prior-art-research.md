# Prior Art Research — Patient Appointment & Scheduling Portal

Research date: 2026-08-10. This is a companion piece to `tech-stack-research.md` — that document compared *candidate* stacks for a new build; this one investigates how *real, shipping* booking/scheduling systems (three open source, one closed) actually solve the same problems the project brief calls out: slot generation, double-booking prevention, the appointment status lifecycle, time zone/DST handling, PHI-aware auth/RBAC, and reminder dispatch/dedup.

**Methodology and how to read the citations.** Four codebases were read directly — cloned/fetched and inspected at the source-file level, not recalled from memory or summarized from third-party write-ups — plus a fifth pass searching for genuine first-party engineering-blog content from healthcare/scheduling companies. Every code citation below is pinned to a specific commit SHA (for OpenEMR and Easy!Appointments, which are under very active development and whose line numbers will drift day to day) or to the `main` branch (for Cal.com and Medplum, where the specific files cited were independently re-fetched and diffed against `main` HEAD at research time to confirm currency). A representative sample of the claims below — repo metadata, exact code snippets, exact schema definitions, exact line numbers — was independently re-verified by directly fetching the cited files a second time before this document was written; where a re-check surfaced a discrepancy (see the Easy!Appointments section) it is noted and resolved, not silently dropped. Anything that could not be verified is labeled **Not verified** rather than guessed at.

## 1. Cal.com (open-source booking engine; public repo now `calcom/cal.diy`)

**Repo status, verified 2026-08-10:** `github.com/calcom/cal.com` now redirects to **`calcom/cal.diy`** — 47.4k stars, MIT license, last push 2026-08-08. Cal.com itself went closed-source; `cal.diy` is a community-maintained fork with all Enterprise Edition ("EE") code stripped. The fork's own README states this plainly: *"No enterprise features — Teams, Organizations, Insights, Workflows, SSO/SAML, and other EE-only features have been removed"* and *"Unlike Cal.com's 'Open Core' model, Cal.diy has no commercial/enterprise code."* [github.com/calcom/cal.com](https://github.com/calcom/cal.com) (redirects), [calcom/cal.diy README](https://github.com/calcom/cal.diy/blob/main/README.md). This matters directly for the reminders finding below — the removal is real and recent, and it visibly amputated a whole subsystem.

**Tech stack** (README "Built With", `package.json`): Next.js (16.2.3), React 18.2.0, tRPC for the main API, a separate NestJS REST API (`apps/api/v2`, `@nestjs/core@10.4.20`) for the platform/public API, Prisma 6.16.1 against PostgreSQL (`>=13.x`) using the `@prisma/adapter-pg` driver-adapter pattern, NextAuth 4.24.13 for auth, Tailwind CSS, Daily.co for video, Turborepo + Yarn workspaces monorepo, Node.js `>=18.x`.

**Slot generation.** Entry point is the tRPC procedure `viewer.slots.getSchedule`, delegating to `AvailableSlotsService` in [`packages/trpc/server/routers/viewer/slots/util.ts`](https://github.com/calcom/cal.com/blob/main/packages/trpc/server/routers/viewer/slots/util.ts). Per-host availability comes from `UserAvailabilityService` ([`packages/features/availability/lib/getUserAvailability.ts`](https://github.com/calcom/cal.com/blob/main/packages/features/availability/lib/getUserAvailability.ts)), which resolves the applicable Schedule + Availability rows (working hours, date overrides, "travel schedule" temporary timezone overrides), pulls OOO/holiday data, calls `buildDateRanges()` ([`packages/features/schedules/lib/date-ranges.ts`](https://github.com/calcom/cal.com/blob/main/packages/features/schedules/lib/date-ranges.ts)) to flatten recurring weekly hours + overrides into UTC `DateRange{start,end}` windows, then subtracts busy time (existing bookings + connected external calendars). Aggregated ranges across all hosts on an event type are then discretized into bookable start-times by `getSlots()` ([`packages/features/schedules/lib/slots.ts`](https://github.com/calcom/cal.com/blob/main/packages/features/schedules/lib/slots.ts)) using event length, offset, minimum booking notice, and slot interval. **In short: availability minus busy time, computed fresh on every read — nothing is pre-materialized as a persisted "open slot" row.**

**Double-booking prevention — three layered mechanisms, verified.**
1. A pre-check (`ensureAvailableUsers.ts`) re-runs availability for the requested slot and throws if nobody's free — a check, not a lock, and race-prone alone.
2. An application-level temporary hold: the `SelectedSlots` Prisma model (`@@unique([userId, slotUtcStartDate, slotUtcEndDate, uid])`, a `releaseAt` expiry) marks a slot as provisionally taken while a user is mid-checkout; `getSchedule` treats other users' unexpired holds as busy time.
3. **The actual atomic backstop is a DB-level unique constraint on the `Booking` table itself**: `idempotencyKey String? @unique`, with the comment *"UID based on slot start/end time & email against duplicates."* It's populated transparently by a Prisma Client Extension — verified directly at [`packages/prisma/extensions/booking-idempotency-key.ts`](https://github.com/calcom/cal.com/blob/main/packages/prisma/extensions/booking-idempotency-key.ts):
   ```ts
   if (args.data.status === BookingStatus.ACCEPTED) {
     const idempotencyKey = generateIdempotencyKey({ startTime, endTime, userId, reassignedById });
     args.data.idempotencyKey = idempotencyKey;
   }
   ```
   where `generateIdempotencyKey` is a deterministic `uuidv5` hash of `${startTime}.${endTime}.${userId}`. Because that column is `@unique` in Postgres, two concurrent INSERTs for the identical host + exact start/end race at the database itself — the loser's INSERT fails on a unique-constraint violation, which is the real, unconditional guarantee (not the pre-check). Cancel/reject nulls the key back out, freeing the slot for reuse. Booking creation runs inside a `prisma.$transaction(...)` block. **Caveat, stated plainly:** this constraint is scoped to *identical* start/end/host — it stops duplicate-submit races on the same exact slot, but doesn't by itself prevent two different-but-overlapping bookings; that's what mechanisms (1) and (2) are for.

**Status lifecycle.** A closed Prisma enum: `CANCELLED | ACCEPTED | REJECTED | PENDING | AWAITING_HOST`. There's no DB-level state machine (no CHECK constraint or trigger) — transitions are enforced entirely in application code: new bookings start `PENDING` or `ACCEPTED` depending on the event type's auto-confirm setting; a single `confirm.handler.ts` endpoint moves `PENDING → ACCEPTED/REJECTED` and explicitly guards re-entrancy (throws if already `ACCEPTED`); `handleCancelBooking.ts` moves any non-cancelled status to `CANCELLED`, guards against double-cancelling and against cancelling a booking whose end time has already passed. `AWAITING_HOST` exists for round-robin/team bookings pending host assignment — its full transition path was **not fully traced**.

**Time zone / DST.** `dayjs` (wrapped as `@calcom/dayjs`). Booking `startTime`/`endTime` are stored as UTC timestamps (`dayjs.utc(...).toDate()`); each Schedule carries its own `timeZone`, and each Attendee row stores its own `timeZone` independently — host and attendee timezones are recorded alongside, not folded into, the UTC instant. DST handling is explicit and commented in code, confirmed directly in `processWorkingHours()` in [`date-ranges.ts`](https://github.com/calcom/cal.com/blob/main/packages/features/schedules/lib/date-ranges.ts):
```ts
// it always has to be start of the day (midnight) even when DST changes
const dateInTz = date.add(fromOffset - offset, "minutes").tz(adjustedTimezone);
...
const offsetDiff = start.utcOffset() - offsetBeginningOfDay; // there will be 60 min offset on the day of DST change
start = start.add(offsetDiff, "minute");
end = end.add(offsetDiff, "minute");
```
In plain terms: it computes the UTC offset at start-of-day versus the offset at the actual working-hours start time, and corrects for the difference — because on a DST-transition day those two offsets differ by 60 minutes, and naively adding "9 hours" to midnight in the wrong offset would shift the entire working-hours window by an hour. This is a deliberate, commented-for-DST fix, not an accident of a timezone-aware library.

**Auth / RBAC.** NextAuth v4, with a custom Prisma-backed adapter and a `CalComCredentialsProvider` (email/password + 2FA + SAML-IdP-aware checks); sessions are JWT-based, and the `jwt` callback embeds a global `role` plus, when in an organization context, an org-specific role resolved from a `Membership` lookup at token-issuance time. Two role layers exist in the schema: a coarse `MembershipRole` enum (`MEMBER | ADMIN | OWNER`) on `Membership` (`@@unique([userId, teamId])`), and a finer-grained PBAC layer — `Role` (nullable `teamId` = global role) with `RolePermission{resource, action}` (`@@unique([roleId, resource, action])`) — enabled incrementally through 2025–2026 (a migration named `enable_pbac_globally` is dated late January 2026, i.e. recent). A separate NestJS platform API (`apps/api/v2`) enforces the same resource/action PBAC model via its own guards, bridging NextAuth JWTs into NestJS's Passport-based auth.

**Reminders / notifications — sharply diminished after the closed-source split.** The full "Workflows" automation engine (email/SMS/WhatsApp/AI-phone-call reminder scheduling, per-step templates, a dedicated `reminderScheduler.ts`) existed as an EE feature and **is now gone from the public fork** — a migration literally titled `drop_workflow_tables` (dated 2026-03-19, after the last tagged release) drops `Workflow`, `WorkflowStep`, `WorkflowReminder`, and related tables, and the `packages/features/ee/workflows` directory no longer exists on `main`. What remains is a single narrow cron job, [`apps/web/app/api/cron/bookingReminder/route.ts`](https://github.com/calcom/cal.com/blob/main/apps/web/app/api/cron/bookingReminder/route.ts), triggered every 15 minutes, that nags organizers (not patients) about *unconfirmed* bookings at 48h/24h/3h after creation. Its **dedup mechanism** is a `ReminderMail` table keyed by `(referenceId, reminderType)`: before sending, it queries for an existing row at that interval bucket and skips bookings already reminded, writing a new row immediately after a successful send — application-level dedup via a persisted "already sent" marker, not a DB unique constraint. **Not verified:** whether the now-deleted historical Workflows engine had its own DB-level dedup guard, since the code is gone from the current tree.

## 2. Medplum (open-source, FHIR-native healthcare platform)

**Repo status, verified 2026-08-10:** `github.com/medplum/medplum` — 2,603 stars, Apache 2.0. Last push same day as research (2026-08-10); latest tagged release **v5.1.29** (2026-08-09), with a continuous release history back through 2023 — genuinely active. Cloned at commit `a3fc52cd2947f47349d65d8ced95dc1dbaab568d`; citations below are pinned to that commit and independently re-confirmed against `main` HEAD.

**Tech stack** (README): "Full-stack TypeScript... Node.js to power our servers, and React to power our frontend apps." Core technologies: **PostgreSQL** (primary data store), **Redis** (background jobs/caching), **Express** (API server), TypeScript, React. Bots (custom serverless functions) run on AWS Lambda; infra-as-code lives in an AWS CDK package — the platform's own hosted offering is AWS-centric, though it's self-hostable.

**Scheduling model — implements FHIR's Schedule/Slot/Appointment resources directly**, and one specific design decision stands out: per [medplum.com/docs/scheduling](https://www.medplum.com/docs/scheduling), a Slot "only exists in the datastore for booked or blocked time — free slots are computed on demand," never pre-materialized. A `SchedulingParameters` extension on `HealthcareService` sets shared defaults (duration, alignment interval/timezone); a `Schedule` can override per-actor via a nested `availability` extension (`daysOfWeek` + `availableStartTime`/`availableEndTime`). In source, [`packages/server/src/fhir/operations/utils/scheduling.ts`](https://github.com/medplum/medplum/blob/main/packages/server/src/fhir/operations/utils/scheduling.ts): `resolveAvailability()` expands those windows into concrete intervals per day; `applyExistingSlots()` subtracts existing `busy`/`busy-unavailable`/`busy-tentative` Slot intervals. A Schedule is constrained to exactly one actor — `getSchedulingParametersGroup()` throws `badRequest('Scheduling only supported on schedules with exactly one actor', ...)` if violated. Blocked/busy time is represented as a real, persisted `Slot` resource with `status: 'busy-unavailable'` for manual provider blocks (vacation, admin time), and synthetic `busy`/`busy-unavailable` proposed slots for the appointment itself plus any `bufferBefore`/`bufferAfter` prep/cleanup padding (`packages/server/src/fhir/operations/find.ts`). **Caveat stated by the project itself:** the `$find`/`$hold`/`$book`/`$confirm`/`$cancel` operation handlers are each explicitly marked `@experimental — Scheduling Beta API` in their own JSDoc, and the docs page is labeled "(Beta)" — treat the whole booking flow as beta by Medplum's own characterization, not a mature, long-hardened feature.

**Double-booking prevention — the strongest concurrency guarantee found in this research, and directly verified.** `createProposedAppointment()` wraps Slot/Appointment creation in `repo.withTransaction(..., { serializable: true, resourceTypes: ['Appointment', 'Slot'] })` and **re-validates availability inside the transaction** before writing — closing the read-then-write race between `$find` and `$book`. Confirmed directly in [`packages/server/src/fhir/repository/repository-connection.ts`](https://github.com/medplum/medplum/blob/main/packages/server/src/fhir/repository/repository-connection.ts): `const isolationLevel = options?.serializable ? 'SERIALIZABLE' : 'REPEATABLE READ'` followed by `BEGIN ISOLATION LEVEL ' + isolationLevel`. This is a genuine Postgres **`SERIALIZABLE`** transaction — the strongest isolation level Postgres offers — used specifically so two concurrent bookings of the same slot can't both commit. On a serialization failure (Postgres SQLSTATE `40001`), the transaction is automatically retried with jittered exponential backoff (default 2 attempts, 50ms base delay). `$confirm` and `$cancel` use the same `serializable: true` pattern when flipping `busy-tentative → busy` or deleting slots on cancellation.

**Status lifecycle.** Confirmed in [`packages/fhirtypes/dist/Appointment.d.ts`](https://github.com/medplum/medplum/blob/main/packages/fhirtypes/dist/Appointment.d.ts) and re-verified independently: `status: 'proposed' | 'pending' | 'booked' | 'arrived' | 'fulfilled' | 'cancelled' | 'noshow' | 'entered-in-error' | 'checked-in' | 'waitlist'` — FHIR R5's value set, reproduced verbatim (this is a spec-mandated closed enum, not a project-specific choice). Real transitions are implemented per operation: `$find` synthesizes `proposed`; `$hold` sets `pending` and marks slots `busy-tentative`; `$confirm` (allowed only from `pending`/`proposed`) sets `booked` and flips slots to `busy`; `$book` sets `booked` directly; `$cancel` (allowed only from `pending`/`booked`) sets `cancelled` and **deletes** the associated Slot resources, freeing the time.

**Time zone / DST.** Per the dedicated doc page [medplum.com/docs/scheduling/timezones](https://www.medplum.com/docs/scheduling/timezones): FHIR `date`/`dateTime` values are "preserved exactly as submitted" — Medplum does not silently normalize to UTC, it stores whatever offset was given. Actor timezone is carried via the standard FHIR `http://hl7.org/fhir/StructureDefinition/timezone` extension on `Organization`/`Location`/`Practitioner`; `getSchedulingParametersGroup()` throws `badRequest('No timezone specified', ...)` if a referenced actor has none. The docs recommend storing local time + timezone + recurrence rule for recurring events rather than collapsing to a single UTC instant. At the code level (not documented on the timezone page itself), `scheduling.ts` uses the `temporal-polyfill` library's `Temporal.ZonedDateTime`/`Temporal.Instant` rather than raw JS `Date` arithmetic — `Temporal` is DST-aware by construction.

**PHI handling, encryption, compliance.** [medplum.com/docs/compliance](https://www.medplum.com/docs/compliance) states Medplum holds SOC2 Type II, HITRUST e1, ONC Certification, CLIA/CAP, and CFR Part 11 certifications, with a BAA/MSA available on request ([medplum.com/docs/compliance/hipaa](https://www.medplum.com/docs/compliance/hipaa): *"Medplum is HIPAA Compliant"*), scoped to Medplum's hosted environment (self-hosting is offered as an alternative). [medplum.com/security](https://www.medplum.com/security) states AES encryption at rest, TLS 1.2/1.3 + AWS WAF in transit, per-customer dedicated AWS trust zones, and annual third-party pen testing. Audit logging is **not** advertised on the compliance pages themselves but is real and automatic in code: `packages/server/src/fhir/repo.ts` calls `this.logEvent(...)` generating a FHIR `AuditEvent` on essentially every data-access path (create, read, history, update, delete, patch, search) — i.e. audit logging is a property of the data-access layer itself, not a documented customer responsibility.

**Auth / RBAC.** [medplum.com/docs/access/access-policies](https://www.medplum.com/docs/access/access-policies): an `AccessPolicy` resource restricts read/write per resource type or per field (`readonlyFields`/`hiddenFields`), with `criteria` using FHIR search syntax (e.g. `Patient?address-state=CA`) for row-level scoping, and compartment-based patient self-scoping via `Patient?_compartment=%patient` where `%patient` resolves against the authenticated user's own `ProjectMembership`. Default policies map close to the brief's three roles: **Practitioner** — read/write clinical types, read-only on reference data; **Admin** — unrestricted; **Patient** — restricted to their own compartment; **RelatedPerson** — parameterized access to their associated patient's compartment. `ProjectMembership` binds a user to a project (or specific compartments within it) and references an `AccessPolicy`. `ClientApplication` is documented separately for server-to-server auth ([medplum.com/docs/auth/client-credentials](https://www.medplum.com/docs/auth/client-credentials)).

**Reminders / notifications — no built-in dispatcher; explicitly left to the implementer.** No shipped appointment-reminder feature was found. The building blocks exist — **Bots** ([medplum.com/docs/bots](https://www.medplum.com/docs/bots): serverless functions, "similar to AWS Lambda... easy to write and deploy and trigger with FHIR Subscriptions") and **Subscriptions** ([medplum.com/docs/subscriptions](https://www.medplum.com/docs/subscriptions): standard FHIR event-driven webhooks) — plus a documented Twilio SMS integration (`Communication/$send-sms-twilio`, [medplum.com/docs/integration/twilio-sms/sending-sms](https://www.medplum.com/docs/integration/twilio-sms/sending-sms), whose example payload text "Your appointment is tomorrow at 10am" hints at intended use). But no shipped bot example, cron job, or scheduled-notification template for appointment reminders specifically was found anywhere in the repo's examples, docs, or blog. **This is a real, notable gap** relative to the brief's reminder requirement — Medplum gives you the primitives, not the feature.

## 3. OpenEMR (long-running open-source EMR/practice-management system)

**Repo status, verified 2026-08-10:** `github.com/openemr/openemr` — created 2010-05-21, 5,356 stars, 3,002 forks, last push same day as research. Latest release `v8_2_0` (2026-07-08). Cloned/fetched at commit `feaf85c14185942ca0d68734a7d63e0b4b8de035`; all citations pinned there and independently re-checked against that exact commit (a second check against the wrong branch initially produced a false negative for one schema detail — resolved by re-fetching the pinned commit, matching exactly).

**Tech stack** (`composer.json`): PHP `>=8.3`, MySQL/MariaDB (`ext-mysqli`/`ext-pdo_mysql`), with `doctrine/dbal ^4.4`, `doctrine/orm ^3.6`, and `doctrine/migrations ^3.9` layered on top of a large body of legacy raw-SQL/`mysqli` code, Symfony components (console, DI, HTTP client), Laminas MVC/forms, `monolog/monolog`, `league/oauth2-server`+`lcobucci/jwt` for OAuth2/JWT (backing its FHIR API), and `adodb/adodb-php` (still present, used by the vendored ACL library). Frontend build requires Node 24.x. **This is genuinely a 20+ year-old core continuously modernized with a modern shell** — useful precisely as the contrast case the brief's research framing anticipated.

**Scheduling module — a free-form calendar, not a generated bookable-slot system.** The calendar UI (`interface/main/calendar/`) is, per its own file header, **a fork of the PostCalendar module from the PostNuke content-management system** — `interface/main/calendar/index.php` literally states "POST-NUKE Content Management System... Based on: PHP-NUKE Web Portal System." A provider's working hours aren't a separate "schedule" entity — they're modeled as an ordinary recurring calendar event in a special category (`openemr_postcalendar_categories` seeds `in_office`, `out_of_office`, `vacation`). `getAvailableSlots()` in [`library/appointments.inc.php`](https://github.com/openemr/openemr/blob/feaf85c14185942ca0d68734a7d63e0b4b8de035/library/appointments.inc.php) (confirmed at lines 507–591) scans existing events, treats "In Office" as the availability anchor and "Out Of Office" as excluded, and walks forward in `getSlotSize()`-minute increments (a **clinic-wide global default**, not per-provider — `interface/globals.php` defaults `calendar_interval=15`) until the next appointment. This is exposed as an optional "Find Available Appointments" popup, invoked from a separate button on the event-editing screen — **a lookup helper, not a gate enforced on every save.**

**Double-booking prevention — weak to absent, verified directly against the schema.** The `openemr_postcalendar_events` table's own DDL was fetched and confirmed to contain only `PRIMARY KEY (pc_eid)`, a non-unique composite index `basic_event (pc_catid, pc_aid, pc_eventDate, pc_endDate, pc_eventstatus, pc_sharing, pc_topic)` for query performance, a non-unique index on `pc_eventDate`, and `UNIQUE KEY uuid (uuid)` on a surrogate FHIR-compliance column — **there is no unique constraint on any combination of provider + date + time.** `InsertEvent()` in `library/encounter_events.inc.php` runs a plain `INSERT` with no preceding existence check, no transaction, and no row lock. The newer FHIR/REST path (`src/Services/AppointmentService.php::insert()`) validates field types and referential integrity but likewise performs no overlap check before its unconditional `INSERT`. The only overlap-aware code anywhere is the opt-in "Find Available Appointments" popup — advisory, not enforced. **Verdict, stated plainly: two concurrent bookings (via the UI or the API) for the same provider/time will both succeed with no error.** This is the clearest "what not to do" reference point found across all four codebases for the brief's single most safety-critical requirement.

**Status lifecycle.** `pc_apptstatus varchar(15) NOT NULL default '-'` — confirmed exactly against the live schema. Values are seeded via a `list_options` table (`list_id='apptstat'`) as single-character codes chosen so a color-coded letter renders directly on the calendar grid: `-` none, `*` reminder done, `+` chart pulled, `x` cancelled, `?` no-show, `@` arrived, `~` arrived late, `!` left without visit, `#` insurance/financial issue, `<` in exam room, `>` checked out, `$` coding done, `%` cancelled <24h, `^` pending, plus `AVM`/`SMS`/`EMAIL`/`CALL`-prefixed confirmation states. Transition logic is embedded directly in PHP (`library/appointment_status.inc.php::updateAppointmentStatus()`), e.g. a `$` (coding done) status is treated as terminal, and a transition from `>` (checked out) back to `<` (in exam room) is explicitly blocked.

**Time zone / DST — naive local time, single system-wide zone.** Schema types are all naive: `pc_eventDate date`, `pc_startTime time`, `pc_endTime time` — none carry an offset or zone identifier. There is exactly one timezone setting for the entire installation (`gbl_time_zone` in `interface/globals.php`), which synchronizes PHP's process timezone and the MySQL session's `time_zone` at bootstrap. There is no per-facility, per-provider, or per-appointment timezone field anywhere — this confirms a single-clinic/single-timezone deployment model, and a DST-transition-week appointment is inherently ambiguous at the storage layer since no offset is ever recorded per row.

**RBAC / access control.** OpenEMR vendors and wraps the old **phpGACL** library directly — `src/Gacl/Gacl.php`'s own docblock states "Original code from phpGACL." `src/Common/Acl/AclMain.php` is the enforcement entry point, evaluating four access levels (`view`, `write`, `wsome`, `addonly`) across named ACO sections including `patients/appt` ("Appointments"). Default installed roles: Administrators, Physicians, Clinicians, Front Office, Accounting, and a dedicated **Emergency Login (breakglass)** role. Scheduling-relevant grants at install: Front Office gets `write` on `patients→appt` and `groups→gcalendar`; Clinicians get `write` on `patients→appt` plus encounter-level grants; Administrators get blanket write.

**Audit logging / HIPAA.** Two subsystems: a general `log` table (with a `checksum` column for tamper-evidence), and a modern [`src/Common/Logging/EventAuditLogger.php`](https://github.com/openemr/openemr/blob/feaf85c14185942ca0d68734a7d63e0b4b8de035/src/Common/Logging/EventAuditLogger.php), confirmed directly to contain the comment *"IMPORTANT: this connection must be separate from the main application"* connection (line 42) — a deliberate design choice for audit-log integrity independent of the app's main DB session — plus checksum fields (line 693–694), a first-class `Scheduling` event category, optional **ATNA** (IHE Audit Trail and Node Authentication) export for real healthcare-interoperability audit standards, and breakglass-access tracking tied to the Emergency Login role. **Not independently verified:** any HIPAA-specific marketing/wiki language (not fetched this session) — but the code-level mechanism (append-only log, separate connection, checksums, ATNA export) is a real, functioning implementation, not just a documentation claim.

**Reminders / notifications — real, with a simple row-flag dedup pattern.** `src/Common/Command/PhoneNotificationCommand.php`, a Symfony Console command documented "Intended to run hourly from cron," replaced a legacy batch script. Dedup happens in two layers: the query that selects candidate appointments filters out any already-notified row (`pc_sendalertsms='NO'`), and after a successful send the appointment row itself is updated (`pc_sendalertsms='YES'` / `pc_sendalertemail='YES'`) — the "already sent" marker lives directly on the appointment row rather than in a separate outbox table. A `notification_log` table additionally records each send attempt (message, gateway info, timestamp) for audit/history. Phone reminders route through a third-party voice-call gateway ("Maviq"); SMS/email use parallel code paths sharing the same flag-on-row dedup pattern.

## 4. Easy!Appointments (smaller open-source appointment-booking app)

**Repo status, verified 2026-08-10 — with a correction.** `github.com/alextselegidis/easyappointments` — 4.3k stars, 4,087 commits, actively maintained (latest commit on `main` from the same day as this research). The public-facing 1.6.0 tag is dated 2026-05-27. **An initial independent re-check of this codebase against the repo's stale `master` ref produced apparent contradictions** (a claimed `has_provider_conflict()` method and `Calendar.php`/`Booking.php` controllers appeared to be missing). Re-checking against the repo's actual default branch and the exact commit originally cited (`359c3649dc1977fa3fe882b422a462d77c8abce4`, 2026-07-29) resolved this cleanly: **every specific claim below — file names, function names, and line numbers — was confirmed to match exactly** once the correct ref was used. This is flagged here as a methodology note: this repo's default branch changed at some point, and citing a pinned commit SHA (as done throughout this document) is what made the discrepancy resolvable rather than a silent error.

**Tech stack** (`composer.json`, `package.json`, `docker-compose.yml`): PHP `>=8.2`, classic CodeIgniter-derived MVC structure (`application/controllers`, `application/models`, `application/libraries`), Bootstrap 5.3, FullCalendar 6, jQuery 3.7, moment/moment-timezone, MySQL 8.0. Server-rendered, jQuery-driven — **has not migrated to a modern `src/`-based or SPA layout**, unlike the direction OpenEMR is heading with Doctrine/Symfony.

**Slot generation.** [`application/libraries/Availability.php`](https://github.com/alextselegidis/easyappointments/blob/359c3649dc1977fa3fe882b422a462d77c8abce4/application/libraries/Availability.php) (647 lines). `get_available_periods()` decodes the provider's `working_plan` JSON (per weekday) or a date-specific override from `working_plan_exceptions`, builds the day's initial `[start, end]` period, then **subtracts** breaks, existing appointments, unavailabilities, and blocked periods using explicit left/middle/right interval-splitting logic. `generate_available_hours()` then walks the remaining free periods in `slot_interval`-minute steps (service-configurable, default 15 min), emitting a slot only where the remaining time in a period is ≥ the service's duration. A separate `consider_multiple_attendants()` path handles group/class services by counting existing bookings per slot and offering it only while capacity remains. **Same general shape as Cal.com's algorithm** (availability windows minus busy/blocked intervals, computed on read) despite the very different tech stack.

**Double-booking prevention — the project's own code says this out loud: it's a race.** No DB unique constraint exists anywhere in the schema (every migration was checked; zero `UNIQUE` keys on the appointments table beyond the auto-increment primary key). No transaction or row lock is used around appointment creation (`Appointments_model::save()` calls `validate()` then `insert()`/`update()` as separate, non-transactional calls). A real conflict-check method does exist — `has_provider_conflict()`, confirmed at exactly [`application/models/Appointments_model.php`, lines 724–746](https://github.com/alextselegidis/easyappointments/blob/359c3649dc1977fa3fe882b422a462d77c8abce4/application/models/Appointments_model.php#L724-L746) — but it is only invoked from the **admin/staff backend** calendar controller ([`application/controllers/Calendar.php`, lines 328–341](https://github.com/alextselegidis/easyappointments/blob/359c3649dc1977fa3fe882b422a462d77c8abce4/application/controllers/Calendar.php#L328-L341)), where staff can even bypass it via a `force_save` flag. **The public customer-facing booking flow never calls it at all** — instead, [`application/controllers/Booking.php`](https://github.com/alextselegidis/easyappointments/blob/359c3649dc1977fa3fe882b422a462d77c8abce4/application/controllers/Booking.php)'s `register()` method (confirmed starting at line 368) relies on `check_datetime_availability()` (confirmed at line 603), which just re-runs the full availability calculation immediately before insert. The method's own docblock (confirmed at line 592) states this plainly:
> *"It is possible that two or more customers select the same appointment date and time concurrently. The app won't allow this to happen, so one of the two will eventually get the selected date and the other one will have to choose for another one."*

This is an honest, self-documented pre-check-then-insert race window with **no DB-level guarantee behind it** — the project's own comment describes optimistic, unlocked, best-effort behavior, not a correctness guarantee. Alongside OpenEMR, this is the second clear "weak guard" reference point among the four codebases studied.

**Status lifecycle.** `status` is a free-text `VARCHAR(512)`, not an enum. Default values (`["Booked", "Confirmed", "Rescheduled", "Cancelled", "Draft"]`) are seeded as an admin-editable JSON setting via the Business Settings UI — fully open-vocabulary, unlike Cal.com's closed Prisma enum or Medplum's FHIR-mandated set. No state-machine or transition-guard code was found anywhere; any actor permitted to edit the field can set it to any configured value directly (e.g. nothing prevents `Cancelled → Confirmed`).

**Time zone / DST.** `start_datetime`/`end_datetime` are plain naive MySQL `DATETIME` columns with no stored offset. Providers have a `timezone` field, and server-side availability math (e.g. book-advance-timeout calculations) uses PHP's IANA-backed `DateTimeZone`, which is DST-correct for that purpose. However, **the customer's timezone selector is display-only, client-side**: `assets/js/http/booking_http_client.js` uses `moment-timezone` to re-render the shown time in the customer's zone, but the underlying `data-value` on the slot button stays the provider-local string, and the booking submission (`assets/js/pages/booking.js`) builds `start_datetime` from that original provider-local value — **not** the converted one. Net effect: what's actually persisted is always the provider's local wall-clock time; there is no UTC normalization anywhere in the storage layer, and the customer-facing timezone conversion is cosmetic only.

**Auth / RBAC.** Four seeded roles (Administrator, Provider, Customer, Secretary), each with per-resource **integer bitmask** permission columns (`PRIV_VIEW=1, PRIV_ADD=2, PRIV_EDIT=4, PRIV_DELETE=8`, 15 = full CRUD) across resources (appointments, customers, services, users, settings). A global `can($action, $resource)` / `cannot(...)` helper reads the current session's role and gates controller actions. Beyond the flat role matrix, `Permissions::has_customer_access()` adds row-level scoping: when `limit_customer_access` is enabled, a provider/secretary can only touch a customer they've had a prior appointment with, and secretaries are further scoped to their assigned providers via a join table.

**Reminders / notifications — no scheduled reminder job exists at all.** `application/libraries/Notifications.php` sends **synchronous transactional emails only**, fired immediately at save/delete time, to customer + provider + notification-enabled admins + assigned secretaries. No SMS capability exists anywhere in the codebase (grepped app-wide; zero matches for any SMS provider). The only "reminder" concept present is a `VALARM` block embedded in the generated `.ics` calendar attachment (`application/libraries/Ics_file.php`) — a calendar-client-side alarm handled by Google Calendar/Outlook, not a server-scheduled reminder. The CLI (`application/controllers/Console.php`) exposes `install`, `migrate`, `seed`, `backup`, `sync`, and `cleanup` commands but **no `remind`/notify command** — confirming there is genuinely nothing analogous to the brief's "24h-prior reminder" requirement built in.

## 5. Bonus find: CareCode Open HMIS (`hmislk/hmis`) — a genuinely different domain-modeling choice

Found via a broader search for other real, actively-maintained open-source healthcare-scheduling systems (several other hits — e.g. a popular PHP hospital-management tutorial repo — were checked and rejected as toy/stale). This one is real: per its own README it has served "over 40 healthcare institutions since 2004," open source since 2012, and its own commit log showed activity from the same day as this research. Tech stack is Java/Jakarta EE — JSF via PrimeFaces, EJB, JPA/EclipseLink, MySQL/MariaDB — a meaningfully different generation and ecosystem than the other three OSS projects here.

The interesting finding is architectural, not just technical: HMIS's scheduling module is called **"Channelling"** and models a **queue/token system rather than minute-level time slots** — a patient gets a `serialNo` (a booking/token number) within a doctor's `SessionInstance` (one doctor's appointment-time block), matching how South Asian outpatient "channelling centres" actually run (this is a Sri Lankan-origin project). Its concurrency guard is also structurally different from either Cal.com/Medplum's DB-transaction approach or OpenEMR/Easy!Appointments' absence of one: the serial-number-assignment methods in `ServiceSessionBean` are annotated `@Lock(LockType.WRITE)` on a container-managed `@Singleton` EJB — under Jakarta EE's concurrency model this forces the container to serialize all calls to that method within one app-server instance, so two patients genuinely cannot receive the same serial number for the same session concurrently. **Caveats, explicitly not resolved:** it wasn't traced whether the final booking/bill persistence happens inside that locked scope or just after it; a container-level lock like this provides no protection across a horizontally-scaled multi-instance deployment; and no `@UniqueConstraint` was found on the underlying JPA entities as a DB-level backstop if the app-level lock were ever bypassed. Useful primarily as evidence that "queue position" is a legitimate alternative domain model to "discrete calendar slot" for outpatient scheduling — a genuinely different framing than every other system studied here.

## 7. Synthesis — what recurs across independent implementations, and what's a genuine judgment call

### What recurs (the "obvious right way" — converged on independently by unrelated teams)

1. **Slots are computed on read from availability minus busy time; nothing is pre-materialized as a persisted "open slot" row.** Medplum states this as an explicit design decision (a Slot "only exists in the datastore for booked or blocked time"); Cal.com's `getUserAvailability` → `buildDateRanges` → subtract-busy-time pipeline and Easy!Appointments' period-splitting `Availability.php` do the identical computation shape despite being built in completely different languages a decade apart. Even OpenEMR's much weaker "Find Available Appointments" popup is doing the same subtraction, just as an optional lookup rather than a core primitive. **Takeaway for this project: generate slots at query time from (working hours ∪ date overrides) − (breaks ∪ blocked time ∪ existing bookings); don't store a slot table that has to be kept in sync.**

2. **The real double-booking guard is a database-level mechanism, and a pre-check query alone is explicitly known to be insufficient — the codebases that skip the DB-level guard say so themselves.** Medplum uses full Postgres `SERIALIZABLE` isolation plus in-transaction re-validation and automatic retry-on-conflict. Cal.com uses a `UNIQUE` constraint on a derived idempotency key as the unconditional backstop, layered under a softer temporary-hold table. Both are real, different, and both work. By contrast, Easy!Appointments' own docblock *admits* its public booking path is a race ("it is possible that two or more customers select the same appointment date and time concurrently... one of the two will eventually get the selected date"), and OpenEMR has no guard at all on its primary save path — confirmed directly against the live schema. **This is the single clearest, most load-bearing convergence for the project's pass/fail concurrency requirement: a pre-check-then-insert pattern is a known-inadequate pattern, not a hypothetical risk — two of four real systems studied ship it anyway, and both document or evidence real double-booking exposure as a result.**

3. **Times are stored as an unambiguous instant (UTC, or an explicitly-preserved offset) plus a separately-recorded per-actor timezone — never a naive local string, in every system that handles multi-timezone use at all.** Cal.com stores UTC + independent `timeZone` fields on both Schedule and each Attendee row. Medplum preserves the submitted offset exactly and requires an explicit timezone extension on any scheduled actor (throwing if absent). The two systems that *don't* do this — OpenEMR (one global process-wide timezone, naive `date`/`time` columns) and Easy!Appointments (naive `DATETIME`, customer-timezone conversion is display-only and never reaches storage) — are also the two systems with no real multi-timezone story at all, which is a fully consistent pattern: naive local storage and multi-timezone correctness don't coexist in any system studied. **Takeaway: store UTC, store each party's IANA timezone identifier separately, and never let a "converted for display" value leak back into what gets persisted (Easy!Appointments' actual bug).**

4. **RBAC is modeled as role → permission grant, plus a second, independent row-level/compartment ownership filter — every system studied has both layers, even the 20-year-old one.** Medplum's `AccessPolicy` + FHIR compartment (`%patient`); Cal.com's PBAC `Role`/`RolePermission` plus org/team `Membership`; OpenEMR's phpGACL role→ACO grants (no row-level layer found beyond role scoping — a genuine gap in that specific system, not a counterexample to the pattern being desirable); Easy!Appointments' bitmask role matrix plus its separate `has_customer_access()` row-level check. **Takeaway: "role has permission on resource type" is necessary but not sufficient — a second explicit check that the row belongs to this specific actor is what every system that takes this seriously adds on top, matching exactly what the project brief already specifies (RLS or explicit server-side ownership checks).**

5. **Reminder/notification dedup is done via a persisted "already sent" marker checked immediately before send — never by trusting that a cron job won't overlap with itself.** Cal.com's `ReminderMail` table keyed by `(referenceId, reminderType)`; OpenEMR's boolean flag directly on the appointment row (`pc_sendalertsms`/`pc_sendalertemail`) checked in the candidate-selection query, flipped immediately after a successful send. Both are simple, both are application-level (no DB unique constraint enforcing it), and both converge on the same shape: query excludes already-sent, write the "sent" marker as close to the send call as possible. **Takeaway: this is a solved, simple pattern — a per-appointment-per-interval sent-flag or table row, checked in the same query that selects candidates.**

### What varies — genuine judgment calls with no single "right" answer in the prior art

1. **Isolation-level strategy on the concurrency guard itself.** Medplum reaches for full `SERIALIZABLE` + automatic retry — the heaviest, most pessimistic-adjacent option Postgres offers, chosen specifically because it lets the availability check and the write happen with the database itself guaranteeing no interleaving. Cal.com instead relies on a `UNIQUE` constraint as the hard backstop, with a softer, expiring "temporary hold" table doing most of the day-to-day conflict avoidance — architecturally closer to optimistic concurrency with a strict final gate. Neither is "the" answer; they're different points on the same spectrum, and the choice likely depends on how much the team trusts a unique-key-on-conflict-derived-value to actually cover the specific overlap patterns that matter (Cal.com's key only covers *identical* start/end, not general overlap — worth being aware of if adopting that specific pattern rather than the SERIALIZABLE one).

2. **Status vocabulary: closed enum vs. open, admin-configurable list.** Medplum inherits FHIR's fixed 10-value `Appointment.status` set (a spec constraint, not a product choice). Cal.com uses a small closed Prisma enum. Easy!Appointments makes `status` an admin-editable free-text list with zero transition guards anywhere in the code. OpenEMR sits in between — a large, extensible-in-theory but effectively-fixed-in-practice single-character code table with some hard-coded terminal-state logic. This is a real design fork: a closed enum buys you compile-time/DB-level exhaustiveness checking and makes "only valid transitions allowed" easy to enforce; an open list buys configurability at the cost of needing to hand-write every transition guard yourself (which Easy!Appointments simply didn't do). The project brief's explicit requirement ("only valid transitions are allowed... invalid transitions are rejected server-side") points toward the closed-enum-with-explicit-guards side of this fork, not the open-list side.

3. **How much of "reminders" ships as a real, hardened feature versus a thin afterthought.** This is the weakest area across every system studied, open-source or closed. Medplum offers no built-in appointment-reminder feature at all — Bots and Subscriptions are generic primitives, not a shipped reminder pipeline. Cal.com *had* a full reminder/workflow engine, but it was Enterprise-only and is now entirely gone from the actively-developed open fork, leaving only a narrow "nag the organizer about unconfirmed bookings" cron. Easy!Appointments never had a scheduled reminder job at all — only immediate transactional email plus a calendar-client-side `.ics` alarm. OpenEMR is the one system with a real, working, cron-driven reminder dispatcher with row-flag dedup — notable precisely because it's the *oldest* codebase studied, not the newest. **Takeaway: prior art does not hand you a proven reference implementation for the reminder-idempotency requirement the way it does for slot generation or RBAC — this is squarely a "build it carefully yourself" area, and OpenEMR's simple flag-on-row-plus-log pattern is the most directly reusable idea found, not any of the more "modern" systems' approach.**

4. **Whether double-booking prevention is DB-enforced at all is genuinely bimodal, not a spectrum — and it splits cleanly along "was this booking-creation path built or substantially rewritten in the last ~5 years" rather than along language/stack lines.** Medplum (TypeScript, new) and Cal.com (TypeScript, new) both have real DB-level guarantees; OpenEMR (PHP, 20+ years, calendar module literally forked from a 2001 CMS) and Easy!Appointments' actual public-booking path (PHP, honestly self-documented as a race) both don't. This is worth calling out explicitly for this project precisely because it's the brief's single pass/fail-gated requirement (20 of 100 points) — prior art shows this is not a hard problem technically (both correct patterns found are a few dozen lines of code), but it is very easy to *skip* if a pre-check query "looks like it works" in manual testing, which is exactly the failure mode Easy!Appointments' own comment describes.

5. **HIPAA/compliance posture ranges from "the whole product's value proposition" to "not mentioned at all."** Medplum is built and marketed explicitly as a HIPAA-compliant platform with a BAA available on request and multiple named certifications (SOC2 Type II, HITRUST e1, ONC). OpenEMR has serious, real compliance machinery in the code (separate audit-log DB connection, checksums, ATNA export, breakglass tracking) but this was not found stated as a formal certification/BAA claim in what was checked this session. Cal.com and Easy!Appointments are pure booking-functionality products with no compliance program surfaced anywhere in their docs or code — compliance would be entirely the deploying organization's responsibility if either were used for PHI. **This tracks the project brief's own framing: HIPAA awareness and sound engineering practice (encryption, audit logs, RBAC, no-PHI-in-logs) is achievable and demonstrated by more than one system here without a formal BAA/certification program — that program itself is a business/legal layer on top of, not a substitute for, the engineering patterns already covered above.**

### Honest gaps — not verified in this pass

Medplum's own reminder-dispatch story (confirmed absent as a *shipped* feature, but whether any community Bot examples exist elsewhere was not exhaustively searched); Cal.com's `AWAITING_HOST` full transition path and whether its now-deleted historical Workflows engine had a DB-level reminder-dedup guard (the code is gone from the current tree, so this is unrecoverable without checking a pre-deletion tag); OpenEMR's formal HIPAA/wiki-level claims (the code-level audit mechanism was verified, marketing-level claims were not fetched); the CareCode HMIS bonus finding's transaction boundaries around its `@Lock(LockType.WRITE)` guard. Each is called out inline above at the point it's relevant rather than only here.
